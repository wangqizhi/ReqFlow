# 产品需求与命名

## 名称

推荐 **ReqFlow（需求流）**，仓库名 `reqflow`。Req 来自 requirement，Flow 表达从记录、提交到验证的连续流程。中文可直接称“需求流”。备选为 PromptQueue（强调待提交队列）、DevBrief（强调给 AI 的开发说明）。名称尚未进行商标和域名检索。

一句话定位：**把等待 AI 写代码的时间，用来准备下一轮清晰、可验证的需求。**

## 使用流程

1. 创建项目，填写项目背景、技术栈、代码规范、运行与测试方式等引导词。
2. 随时记录新需求、优化和修复，自动保存草稿；每条需求补充验收条件。
3. 选择本轮需求，调整顺序，预览并复制 Prompt。
4. 确认已提交给 AI 后，将本轮需求标记为执行中。
5. 等待 AI 编码时继续编辑其他需求，准备下一轮 Prompt。
6. 收到实现结果后，记录提交或 PR 地址并进入待验证。
7. 按验收条件记录验证结果；通过则已验证，失败则返回待提交，保留失败原因。

生成 Prompt、复制 Prompt和确认提交是不同操作。仅生成或复制不改变需求状态，避免复制失败或未发送时误报执行中。

## 页面分区

| 分区 | 内容与行为 |
| --- | --- |
| 引导词 | 项目长期上下文、约束、交付规范，支持编辑和版本历史 |
| 新需求 | 类型为 feature 的草稿和待提交需求 |
| 优化和修复 | 类型为 improvement 或 bug 的草稿和待提交需求，可筛选 |
| 执行中 | 已确认提交给 AI 的需求与关联批次 |
| 待验证 | 实现完成但尚未验收的需求，不默认加入新任务 Prompt |
| 已验证 | 验收通过的需求，保留结果、日期和实现关联 |

原始五个分区保留，补充“执行中”便于区分还没发送和正在处理。类型与状态分别建模，修复需求进入已验证后仍保留 bug 类型。

## 需求字段与状态

需求字段：项目、编号、标题、类型、正文、优先级、排序、验收条件、关联需求、创建/更新时间、版本号。修复可附复现步骤、预期与实际表现；优化可附当前问题和目标指标。

状态：`draft → ready → in_progress → pending_verification → verified`。允许 draft 与 ready 互转；执行中取消后返回 ready；待验证失败或已验证后发现回归可返回 ready，必须记录原因。MVP 不支持直接从 ready 跳到 verified。

验收记录包含逐项结果、环境、证据或链接、执行人和时间。仅当所有必需验收项通过时允许进入 verified。没有验收条件的需求可以保存草稿，但不能进入 ready。

## Prompt 规则

Prompt 按“项目上下文 → 引导词 → 本轮目标 → 有序需求 → 验收条件 → 交付要求”输出 Markdown。需求按优先级和手动顺序排列，保留稳定编号，禁止无提示截断。待验证内容仅在用户主动选择“协助验证”模式时作为验证任务输出；已验证内容只作可选背景。

每次生成保存引导词版本、需求版本、模板版本、完整输出和内容哈希。生成之后编辑源需求不修改已有 Prompt；界面提示源内容已变化。提交确认时若版本不一致，要求重新生成或明确提交原快照。不能将仍在执行中的需求重复加入新的开发批次。

MVP 使用确定性模板，不需要调用模型，也不需要保存 AI API Key。以后可增加 AI 辅助润色，但必须预览差异并由用户接受。

## MVP 验收

- 可以创建项目和引导词，按分区记录与筛选需求。
- 自动保存可显示保存中、已保存、失败；刷新后恢复已保存内容。
- 两个页面同时修改同一条需求时，后提交方收到冲突提示，不覆盖已有修改。
- 已生成批次不受后续编辑影响；等待期间新增需求只出现在下一轮。
- 能复制和导出 Prompt，查看历史批次与每条需求的去向。
- 验证失败可重新进入待提交，验证历史不会丢失。

暂不包含自动运行代码、自动判定验证通过、GitHub 双向同步、多用户实时协作。当前要求的 GitHub 同步指本仓库文档上传，与未来产品功能分开。
