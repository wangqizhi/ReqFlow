# ZCode 指派接入方案与开发交接

研究日期：2026-10-21。本文为开发交接文档，本轮只新增文档，未修改业务代码、登录状态或执行需求。

## 1. 目标与结论

让用户在 ReqFlow 的「提交验证 → 指派」中选择 ZCode，执行本人项目的选定需求，展示执行过程，完成后经 ReqFlow Agent 回写「待验证」，保留人工验收。

结论：ZCode 有官方 CLI，官方明确说明外部程序可把 CLI 当作任务执行器，并提供子进程调用示例，因此技术接入有官方依据。现有仓库已有 ZCode 插件及领取、回写客户端标识，无需新建一套需求协议。

但要区分三项：官方支持 CLI 自动化调用；本机安装包是否包含完整运行资源；当前登录账号的 Coding Plan 是否能用于这一 CLI 构建。前一项不能证明后两项，更不能推出「绝无封号风险」。

## 2. 官方依据与账号使用边界

以下优先引用官方维护文档，不把官方仓库中的用户 issue 当作官方承诺。

1. [官方 README：ZCode 命令行版](https://github.com/zai-org/ZCode#zcode-命令行版)：介绍 TUI、Web、Agent CLI 和源码构建入口。无参数启动 TUI，其他 Agent 参数交给 CLI。源码入口与完整发行包不是同一种打包形态。
2. [批量任务与运行记录](https://github.com/zai-org/ZCode/blob/main/apps/zcode-cli/docs/usage/13-automation.md)：明确写明「CLI 可以作为任务执行器」，提供 Node.js `spawn(executable, args, { cwd, env, shell: false })` 示例；要求调用方管理预算、日志、超时及进程树清理。这是 ReqFlow 外部启动 CLI 的直接技术依据。
3. [CLI 命令行参考](https://github.com/zai-org/ZCode/blob/main/apps/zcode-cli/docs/usage/02-cli-reference.md)：说明 `--prompt`、`--cwd`、`--attach`、`--mode`、`--resume`、`--output-format`。`app-server` 是协议服务入口，不能当普通问答子命令使用。文档明确提示不要假定 `--print` 等参数受支持。
4. [CLI 使用指南](https://github.com/zai-org/ZCode/blob/main/apps/zcode-cli/docs/usage/README.md)：不同构建不能只看版本号判断能力；不要只复制一个 `zcode.cjs` 就假设资源完整。
5. [ZCode 用户协议](https://zcode.z.ai/cn/terms)：账号仅限本人使用；不当多账号使用可能导致冻结或关闭；禁止擅自篡改或绕过安全限制；违规使用可能被中止或终止服务。云端服务仍受账号及套餐规则约束。
6. [连接模型与套餐](https://zcode.z.ai/cn/docs/configuration)：账号授权、Coding Plan 与 API Key 是不同接入方式，额度、通道和收费应按实际配置与套餐规则判断。

针对当前场景的判断：本人本机点击指派，通过未修改的官方 CLI 执行自己的编码任务，符合官方文档描述的技术用途；本次未找到仅因外部子进程启动 CLI 就封号的规定。此判断不是官方对 ReqFlow 的认证或零风险保证。

开发边界：不提取、转发或仿造桌面私有令牌，不伪装客户端请求头，不直连逆向网关，不绕过验证码、限额或风控，不轮换账号规避限制，不把个人订阅包装为多人共享模型服务。登录或套餐失败时应展示错误并停止，不加入绕过逻辑。

若需确认 Coding Plan 的长期自动指派权益，可由用户向协议列出的 `user_feedback@z.ai` 询问：本人本机软件通过子进程调用官方 CLI 执行本人编码任务，不共享、不转售、不绕过限额，是否属于允许用途，以及如何计费。本文不要求为了普通本地开发先等待此回复，但不能把未确认权益写成产品承诺。

## 4. 推荐落地路线

### 阶段 A：能力验证，先决定执行形态

先实现可复用的 ZCode 入口描述，区分原生可执行文件、Node bundle 和命令 shim。发现顺序建议为用户显式配置、PATH、已知桌面安装目录；非标准路径允许配置。现有插件更新器的 `zcodeCli` / `REQFLOW_ZCODE_CLI` 机制可供参考，但不要假设其配置已能直接用于桌面后端。

Node bundle 用真实 Node 运行，不能把打包应用的 `process.execPath` 当 Node。检测入口需有时限，分别记录版本与能力。不要仅以 `--version` 成功显示「可执行任务」或「已登录」。不得为了检测自动安装、登录或发起收费模型调用。

在获授权的测试项目中验证一次真实运行，确定模型配置、插件发现和任务回写。若要达到现有 Codex/pi 的交互体验，再单独验证 ConPTY 中 TUI 的依赖、首条任务投递、权限提问、持续输入、缩放、中断和退出。不能从帮助中有 `tui` 就宣称交互已可用。

### 阶段 B：优先实现非交互任务执行

这是风险和接入复杂度较低的首版：启动官方 CLI，持续接收事件与日志，任务执行结束后退出。按钮及终端文案必须写明任务执行/日志，不能宣称支持继续聊天。

概念参数如下，开发时按检测到的官方构建校验：

```text
node <官方安装包中的 zcode.cjs>
  --prompt <执行附件任务且仅处理指定需求的简短指令>
  --attach <UTF-8 任务文件绝对路径>
  --cwd <项目绝对路径>
  --mode <显式配置且经验证的权限模式>
  --output-format stream-json
  --no-color
```

以上是参数数组示意，不是可直接粘贴的多行 shell 命令。任务正文放临时文件；路径和参数经进程 API 传递，不拼接需求文本到 shell，不把令牌放命令行或日志。

显式选择权限模式；官方非交互缺省可能为 yolo，不能依赖这个缺省，也不能直接照搬 Codex 的完全控制参数。先在测试目录验证权限拒绝与交互工具行为。无头模式需要人工确认而不能继续时，应明确提示并结束或进入受支持的处理流程，不能假装任务成功。

如果产品要求首版必须与 Codex/pi 完全一样可交互，则阶段 B 只能作为 PoC，不应冒充交互功能交付；需完成阶段 C 后再开放对应入口。

### 阶段 C：完整交互，按验证结果选一种

1. **ConPTY + 官方 TUI**：复用现有终端输入、输出与缩放。需从官方文档/源码确认初始任务送入方式；不能直接把 Codex 的裸位置参数传法复制给 ZCode，也不能误用会直接进入无头模式的 `--prompt`。验证失败则保持未开放。
2. **官方 app-server**：若要求稳定接收结构化事件、处理提问、恢复会话，研究其实际协议及版本后实现专用适配器。不能套用 Codex app-server 的消息格式；本方案未核对 ZCode 协议字段，不提供杜撰的方法名。

首版无需同时实现两条路线，也无需新建常驻代理服务。

## 5. 任务领取与状态语义

1. 复用现有校验：项目关联目录有效，选中需求已排期、允许 AI 执行、状态有效且没有活动领取记录。
2. 一次指派只允许处理选定 ID；列表指派可合并 Prompt，但不得领取整个项目其他需求。提示词限定范围，桥接调用同时使用 `--ids`。
3. 不为了展示「已指派」就提前完成或伪造领取。区分会话启动与 `execution claim` 的真实成功，插件通过既有原子领取取得执行权。
4. 保持 `executor=ai` 与现有插件领取条件一致；不要未经核对将需求改成 `agent:zcode`，导致插件不能领取。
5. 完成后由 ZCode 插件按 runId、需求版本和批次等现有协议回写待验证；模型文本声称完成或进程退出码为零，均不能直接把需求转成完成。
6. 用户人工验收仍在 ReqFlow。部分完成、崩溃和取消保留真实状态；停止进程不等于释放领取，沿用现有人工确认释放机制，旧 runId 失效规则不能破坏。
7. 保持项目内会话冲突与重复点击保护；核对不同 Agent 指派相同需求时的复用行为，避免显示 Agent 与实际进程不符。

## 6. 运行管理与错误处理

- 无头运行逐行解析 NDJSON，处理分块、未知事件、stderr、非 JSON 错误及最终结果；stdout/stderr 有大小限制，不把整个流当一个 JSON 对象。
- 同时记录退出状态、sessionId（若实际返回）、取消/超时原因和回写结果。未知事件保留可诊断信息，但敏感字段需脱敏。
- 有受控运行时限与取消能力；终止整个子进程树，清理任务文件，防止遗留 Bash/MCP/后台进程。长任务时限应可配置，不照搬内容生成的两分钟限制。
- 登录、套餐、余额不足、429、401 等分开反馈。限流不进行无限重试，账号/风控错误不反复重登或切换凭据。
- 缺 Node、入口损坏、TUI 依赖缺失、插件未安装分别展示可操作提示。桌面包中 CLI 存在但缺资源时，不自动复制或修改上游运行时。
- 使用现有官方登录入口与受支持配置。不得为了判断登录读取并输出凭据内容。
- 非交互首版不接受伪造的终端输入能力；交互版才显示输入及继续沟通入口。

## 7. 验收标准

开发者根据最终选择的执行形态补充有意义的测试，保留 Codex/pi 现有行为。

1. **发现与配置**：标准/自定义安装目录、空格路径、缺 Node/CLI、版本探测超时、能力不足均有正确提示；未启用不出现可用指派按钮。
2. **参数安全**：中文、引号、换行、超长任务文本及特殊字符通过任务文件正确传入，不产生 shell 注入或 Windows 命令行超长问题。
3. **范围与状态**：单条、批量指派只领取指定任务；其他 Agent 已领取时拒绝；重复点击无重复执行；插件成功后才显示真实领取状态。
4. **回写**：真实完成转待验证；人工验收不被替代；部分失败、版本冲突、旧 runId、取消均不误标完成。
5. **生命周期**：正常退出、进程崩溃、用户取消、超时及界面关闭时，日志/状态准确，进程树与临时文件清理符合预期。
6. **模式准确**：无头版正确展示流式日志及需要人工操作的失败；若交互版开放，则实际验证 TUI 首条任务、继续对话、权限询问、缩放和 Ctrl+C。
7. **真实端到端**：在隔离测试项目与测试需求上完成一次指派、领取、实施、检查、待验证回写，记录 CLI 构建、平台、模型/供应商及已确认的计费方式，不记录秘密。
8. **回归**：运行仓库适用的类型检查、Go 检查及指派相关现有测试；验证 Codex/pi 的启动、会话复用和完成关闭行为没有变化。

## 8. 给后续 AI 助手的执行要求

先读本方案与仓库约定，再检查当前发布入口及代码。先做能力验证，报告采用无头执行还是交互终端，并让界面承诺与实际能力一致。按用户后续授权实施，不把本研究当成已经完成账号验证或取得云服务特殊授权。

禁止只改前后端白名单后就宣布支持 ZCode。禁止下载名称相近的第三方 zcode npm 包充当官方 CLI。禁止把官方反馈仓库里的用户 issue 写成官方许可或套餐可用性保证。

本方案外的潜在修复：`ai_cli.go` 现有 `--print` 与当前官方 `--prompt` 的兼容问题应单独核实；若一并修复，明确其用途是内容生成而非编码指派，保留各自的权限和执行目录边界。
