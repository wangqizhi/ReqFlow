# REQ-053：项目间操作隔离

## 结论：本轮不拆 workspace.json

此前 GUI 将整个工作区 `version` 用作乐观并发令牌。Agent/CLI 修改 A 项目后，仍持旧工作区版本的 B 项目表单也被拒绝。这是校验粒度问题，不是 Agent 执行代码期间一直持有业务锁；单纯拆文件会额外影响备份、项目/文件夹管理、跨项目迁移以及现有 CLI/MOD/插件。

1.5.0 保留一个兼容的 workspace.json，新增各项目的 `revision`。界面项目操作提供 `expectedProjectVersions` 与 SHA256 内容令牌 `expectedProjectSignatures`，针对所触及项目校验；其他项目变化可以重读最新工作区、重新应用并提交，不覆盖其他项目的数据。同项目变化仍提示冲突并保留输入。内容令牌忽略派生的附件路径，可检测旧写入方未递增 revision 的情况。

迁移需求同时校验源、目标项目。工作区导入/替换更新所有导入项目的令牌；创建项目、文件夹等全局操作继续比较工作区版本。项目删除、仓库/目录/引导词/需求/批次操作均按项目校验。

## 文件事务安全

旧「读取版本、写临时文件、rename」并非跨进程条件原子事务，两个写入方可能同时通过检查。现在提交阶段通过 `workspace.json.lock` 目录取得互斥，再次读取全局版本并以唯一临时文件替换；校验失败则在项目令牌仍一致时重读重试。

锁仅覆盖持久化提交，不覆盖 Agent 开发/测试、Git 网络操作或需求编辑期间。不同项目仍共享很短的物理文件提交，但不共享长时间执行锁。Windows 暂时拒绝 rename 时有限重试，不先删除原数据文件。并发首次启动通过同一锁初始化，不互相覆盖默认项目。

## 边界和升级说明

- 同项目同时修改不是允许静默覆盖：仍应刷新并确认当前输入。
- 全局操作、迁移双方项目需要联合校验，不承诺所有操作完全无关。
- 为保证跨进程原子提交，GUI 与所有实际写入的 CLI/Agent 可执行文件都需要使用 1.5.0 或更高的这一协议。旧二进制不会遵守新提交锁；内容校验能发现已发生的旧写入，但不能保证新旧写入方混跑时的原子性。本轮不自动安装或调整用户 Agent 可执行文件配置。
- 进程硬终止若遗留 `.lock`，等待 15 秒后报错，不自动抢占活进程的锁。确认全部 ReqFlow/CLI 进程已停止后，人工检查该锁目录；不要删除 workspace.json。
- 超大工作区仍有单文件序列化成本。如以后规模使短提交明显变慢，可评估分项目存储或数据库；那应是带备份、迁移和跨项目事务设计的独立需求。

## 验证

`scripts/review-1.5-core.mjs`：跨项目旧全局版本可安全保存、同项目冲突、迁移目标冲突、全局操作冲突、导入令牌失效、旧写入方内容冲突、6 路初始化、6 个独立进程累计 48 次项目写入无丢失及无残留临时锁。

`scripts/review-1.5-ui.mjs`：界面仍持旧全局版本时，外部操作 B 项目后保存 A 项目新需求成功，且保留 B 项目修改。
