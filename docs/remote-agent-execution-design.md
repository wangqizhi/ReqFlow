# 远程项目执行方案对比（REQ-166 / REQ-179）

更新：2026-10-19。状态：待用户选择；以下新方案仅为设计，未启用自动同步或修改远程执行协议。

## 本次建议：本地编辑与领取，SSH 远程构建

针对“继续使用本地 ReqFlow 插件，构建和测试放服务器”的目标，建议优先试点方案 B。Agent 聊天运行在本机的真实项目镜像目录，沿用本地插件的 cwd 匹配、CLI、版本检查、独占领取和 complete；源码同步到服务器，由本地 Agent 经 SSH 调用远端构建与测试。原方案 A 保留用于需要 Agent 本身在远端运行的项目。

| 比较项 | A：远程 Agent + 本机受限桥接（原方案） | B：本地 Agent + 源码同步 + SSH（新增建议） | C：双端任意编辑 + 双向同步 |
| --- | --- | --- | --- |
| Agent / ReqFlow 插件 | 远端 Agent，需要新增桥接协议和认证 | 均在本机，现有插件可直接使用 | 本地插件可用，远端 Agent 另需身份协调 |
| 源码权威端 | 服务器，无需维护本地完整镜像 | 本机独立 checkout；服务器为执行镜像 | 两端均可写，冲突与删除必须人工决策 |
| 构建测试 | 直接在远端 | 同步屏障成功后 SSH 执行 | 需先冻结双端写入并解决冲突 |
| 新增成本 | 服务、令牌、端口、幂等与远端插件适配 | 同步工具、SSH 包装命令、快照校验 | B 的成本加冲突处理、锁和恢复界面 |
| 适用范围 | 超大仓库、远端 Agent 工具链或远端原生开发 | 本地可容纳源码、远端依赖或算力更合适 | 确实需要交替编辑的专门项目 |
| 本轮建议 | 保留为后续选项 | 优先小规模验证 | 不作为默认自动同步策略 |

### B 的关键边界

1. **绑定真实本地目录**：ReqFlow 的 `project.dir` 指向本机 checkout，另存远端连接、规范路径和同步标识。已有 `ssh://...` 绑定不能直接伪装成本地路径；由用户选定或创建镜像后切换绑定。项目 ID 保持不变。runFile、数据库、附件库、插件配置与凭据均留本机，不同步。
2. **先确认初始基线**：比较两端 Git HEAD 与未提交修改，分别保留快照；远端已有独有修改时先导入或人工合并，禁止第一次同步直接覆盖。同步根目录不得为盘符根、用户目录或共享的生产部署目录。
3. **单写者与按需回传**：本地 Agent 改源码；远端独立工作目录仅构建测试。依赖安装、缓存、二进制、日志与报告不参与源码双向同步。需要回传的生成源码单列白名单，先取到本地临时目录，查看差异后合并，再重新同步测试。
4. **同步屏障必须可执行**：文件监听只能加速，不能证明“当前测试覆盖当前源码”。包装命令等待同步完成和无冲突，核对源码清单摘要，然后运行构建；结束后再次校验，发现运行中源码变化则本次结果标为过期，重新执行。摘要覆盖已跟踪及新增源码和删除记录，排除依赖、缓存与秘密文件；仅比较 Git HEAD 不足以覆盖未提交改动。
5. **执行隔离**：每次 runId 使用独立远端目录或同一项目排他锁；并发 Agent、其他用户不能共享可变构建目录。需要可靠发布产物时，把通过屏障的内容固定成只读快照，再从该快照构建。远端源码镜像与生产目录分开。
6. **失败闭合**：断线、SSH 非零退出、同步冲突、主机指纹变化、磁盘不足或快照不一致时停止构建和成功回写；保留本机运行记录及远端日志。重连后核实 runId 仍有效，重做屏障；不自动释放或重领需求。

### 同步工具与优化

可以使用成熟同步工具作为传输层，ReqFlow 只管理绑定、状态和运行屏障，避免自研双向文件协议。Mutagen 提供同步模式、忽略规则及 `flush`；`flush` 应配合同步状态检查与源码清单校验，不能单独当作不可变构建快照。其安全模式产生冲突时仍需人工处理。[官方同步说明](https://mutagen.io/documentation/synchronization)、[忽略规则](https://mutagen.io/documentation/synchronization/ignores)。

排除清单至少包含 `.git`、`node_modules`、虚拟环境、缓存、构建输出、`.env`、私钥及 ReqFlow 数据；保留依赖锁文件和项目配置。两端独立 Git 仓库，不复制 `.git` 目录。Windows/POSIX 文件名大小写、换行、可执行位及符号链接应在首次预检明确策略；存在同名大小写冲突则拒绝启动。

较简单的单向传输也可用 rsync over SSH。删除传播必须限定到专用镜像根并先检查 dry-run，不能拼成两条反向 rsync 来模拟安全双向同步；rsync 对删除与过滤的具体行为见[官方手册](https://www.samba.org/ftp/rsync/rsync.1)。Windows 所需运行环境与工具版本需在用户机器上验证后选定，不在本次自动安装。

建议提供项目内统一入口（例如 `remote-check`，名称仅为草案）：读取不含密钥的绑定 → 验证本地/远端项目身份 → 获取执行锁 → 同步屏障 → 固定源码快照 → SSH 运行配置好的构建/测试 → 取回日志与白名单产物 → 校验摘要 → 释放锁。SSH 参数通过结构化 argv 传递；远端路径、命令参数按目标 shell 规则转义，禁止将需求正文拼接进 shell。复用 SSH agent 和已校验 host key，不关闭主机密钥验证。

### 给开发客户端的项目引导词草案

> 在当前本地项目目录执行 ReqFlow 插件的领取与完成回写，并在本地修改源码。项目配置的构建、运行、测试使用约定的远程包装入口；先确认绑定和同步屏障成功，再经 SSH 在指定服务器的本次执行快照中运行。禁止在本机用本地测试冒充远端验证。任何同步、SSH、测试或快照校验失败均报告真实状态，不回写为已完成。报告写明服务器别名、远端目录、源码摘要、命令、退出码和产物路径；不要记录密钥。远端生成源码仅按白名单取回并审阅，合并后重新测试。本地插件的 runFile、数据目录与凭据不得同步。

提示词用于表达工作规则；是否真正执行屏障与测试应由包装命令校验，不能只依赖模型自觉。当前插件不会自动识别此绑定或强制执行上述入口，选择 B 后才实施这些能力。

### 试点验收与选择入口

- 用含中文/空格路径、未跟踪文件、删除与重命名的仓库验证清单一致性；测试不依赖本机已安装的运行时。
- 同步中断、远端编辑冲突、执行期间本机改源码、并发执行、远端磁盘不足均不能产生“验证通过”；回传产物需记录摘要并可追溯源码快照。
- 本地插件领取、版本更新、冲突检测和待验证回写保持现有语义；本地项目切换不会匹配到另一个同名远端目录。
- 用一个非生产项目测量首次同步时间、增量同步延迟、仓库大小和日常恢复成本，再决定推广。

## 原方案 A 的详细设计（保留供比较）

日期：2026-10-15。状态：设计讨论稿，等待用户决定是否实施。本轮只实现 SSH 目录绑定，不实现远程领取、转交或自动唤醒编码任务。

## 建议

保留本机 ReqFlow 作为需求、排期、领取与验收的唯一写入端。远程 Codex 负责在服务器项目目录编码，通过受限的桥接服务读取和回写本机任务。第一阶段采用“用户在远程聊天中 @ ReqFlow Agent”的显式触发，不自动创建聊天或调用模型。

远程目录可浏览与远程插件能执行需求是两个独立能力。连接服务器、选中项目和打开目录，都不代表开始执行。跨机器连接与执行授权应分开。

## 已核对的现状

- `plugins/reqflow-agent/skills/execute/SKILL.md` 定义读取、独占领取、实现与 complete 回写，最后停在待验证。
- `plugins/reqflow-agent/scripts/reqflow.mjs` 的 `callCli` 使用本机 `execFile` 启动配置的 ReqFlow 可执行文件，`canonical` 使用本机 realpath，`matchProject` 按本机路径最长前缀匹配项目。远程 Linux/macOS 无法直接访问 Windows exe、盘符和数据目录；新加入的 `ssh://...` 目录也不会被当前插件的 realpath 匹配。
- `readRun` 会生成 runId，并调用 `execution claim`，需求保存客户端、批次、版本与开始时间。已有活动 aiExecution 的条目会跳过。仅仅把需求置为 in_progress 不能绕过独占领取。
- `complete` 校验运行记录、需求版本与批次快照，最终进入 pending_verification；现有事务与跨进程锁应继续复用。
- 本机保存的 runFile 包含快照签名、执行身份与完成上下文。不能让远端另造一个 runId 后直接 complete，也不应把 SQLite 数据库文件同步给远端写入。
- 插件 read/doctor/complete 的启动前版本更新依赖本机 CLI 查询 bundle。未来远端模式也必须经过本机能力与版本协商，不能尝试在 Linux 上启动 Windows 安装器。

OpenAI 官方文档说明，插件可以组合 skills、MCP 服务和运行环境中的 hooks；skill 负责编排，MCP 服务负责实时数据与受控动作。[插件架构](https://developers.openai.com/plugins/concepts/plugins)、[构建技能](https://developers.openai.com/plugins/build/skills)。这些能力本身不提供本项目的跨机器通道，也不能据此推断 @ 插件会自动恢复另一台机器已有的聊天。下面的桥接协议、授权和转交机制均为项目建议，尚未实现。

## 数据通道选择

| 方案 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 本机受限服务 + SSH 反向端口转发 | 不公开端口；复用现有出站 SSH；本地数据库保持单一写入端 | 需本机 ReqFlow 保持运行；需要服务生命周期、令牌和重连 | 首选试点 |
| VPN 内 HTTPS/MCP 服务 | 多台服务器统一接入，支持标准工具调用 | 需证书、认证与网络运维；服务端权限设计更完整 | 后续扩展 |
| 远程 SSH 回 Windows 调用 exe | 可复用原 CLI | 需 Windows SSH 入站及权限；命令参数、输出和跨平台路径处理复杂 | 不作为默认 |
| 同步数据库/共享 workspace.json | 看似简单 | 并发覆盖、锁语义失效、凭据和附件外泄，恢复困难 | 不采用 |

试点中由本机建立 SSH 连接，将远端 `127.0.0.1:<随机端口>` 反向转发到本机 `127.0.0.1:<随机端口>`。远端 Node 桥接脚本请求该端口，本机服务调用同一 WorkspaceService。转发必须只监听 loopback，使用 ExitOnForwardFailure，不能启用面向公网的 GatewayPorts。SSH 用户相同的其他进程仍可能访问 loopback，因此还需要独立的项目令牌。

这不是本轮目录浏览的 SFTP 会话：目录请求目前按需创建有超时的短连接；执行桥接需要独立且可观察的长连接和关闭入口。

## 项目身份与凭据

绑定时登记本机 projectId、连接配置、服务端 host-key 指纹、远端规范路径 realpath 和 connectionId。不能只按项目名称匹配，也不能直接把远端 `/srv/app` 当成本机路径。远程插件发送其 cwd，由本机按“连接身份 + 远端路径最长前缀”匹配；重名项目、重叠路径与符号链接按当前本地规则明确处理。

每次由用户启用桥接生成短期随机令牌，仅授权一个 projectId 和约定动作。令牌与 SSH 凭据不进入仓库、Prompt、命令行参数或日志；远端配置文件权限 0600，本机保存加密配置。支持撤销、过期、重连后轮换。绑定目录本身不发放执行令牌。初期不提供任意 CLI 或 shell 代理接口。

## 建议的最小协议（尚未实现）

- `capabilities`：协议版本、插件版本、服务身份与支持的动作。
- `inspect`：返回该项目可执行的有效排期和 skipped 原因，只读。
- `claim`：携带 batchId、hash、itemVersion、requestId；本机事务领取并签发执行凭据。
- `run-status`：查询是否仍有效、是否已释放、当前需求版本。断网后先查询，再继续。
- `complete`：提交 runId、执行凭据、原始快照标识、逐条 summary/validation；复用当前原子完成规则，返回 outcomes/unprocessed。
- `release`：只允许结束自己持有的运行；不能释放其他客户端的任务。

requestId 用于网络重试幂等；签名快照和执行凭据由本机生成、校验。远端 runFile 只保存恢复所需的项目身份、批次、签名和凭据引用，避免复制整份工作区。普通用户动作仍走现有 UI/CLI。

## “激活本地执行中流程”的两种情况

1. **排期状态为执行中，但尚未被客户端领取**：远程插件经桥接 inspect/claim，成功后正常执行。沿用当前有效 draft/submitted 排期、AI executor、版本和 hash 检查，不扩大到未排期需求。
2. **本机 Codex 已持有活动运行**：远端 claim 必须拒绝。建议第一阶段让用户停止原聊天，在执行中页面释放运行，再由远端重新领取。旧 runId 完成回写必须失败；旧执行记录保留结束时间和用时。

如未来需要无缝转交，应增加独立的“转交到服务器”事务：用户确认源运行已停 → 校验源 runId 与快照 → 原子结束旧运行并创建新运行 → 新凭据只交给目标连接 → 保留来源与审计。不得把 runFile 直接复制给另一台机器并让两个客户端共用身份，也不自动释放超时运行。

## 用户操作草案

1. 在 ReqFlow 绑定远程目录，明确服务器账号、目录和项目。
2. 用户主动开启“允许远程 Agent 连接”，查看授权范围、端口、有效期与连接状态。
3. 在服务器目标目录的 Codex 聊天中安装/配置支持远程模式的插件，然后 @ ReqFlow Agent。
4. 插件读取本机的有效排期，事务领取后在远端实现；测试在远端运行，报告标明运行环境、命令、结果和产物位置。
5. 完成经桥接回写本机待验证；本机界面显示远程客户端、服务器别名、开始/结束时间和摘要。
6. 人工在本机验收。断线显示状态，关闭桥接撤销令牌，但不擅自释放运行。

Codex 聊天本身运行在哪台主机由用户的 Codex 环境决定；插件不应借用未公开的桌面内部 API 来创建或唤醒远端聊天。未来若接入宿主正式支持的远程聊天调度，应单独核对官方接口、用户授权与版本兼容。

## 失败处理与验收门槛

- 双客户端同时领取仅一个成功；本机执行中与远程执行中互斥。
- 完成前用户改需求、换排期、取消、释放或转交时，旧凭据回写拒绝，已写项与未写项明确区分。
- 请求成功但响应丢失时，按 requestId 查询结果，不生成新 runId 反复领取。
- 本机退出/睡眠、网络断线、SSH 主机密钥变化、目录删除时可见失败；远端保留报告待用户恢复，不能打印回写成功。
- 恶意远端不能访问其他项目、读取 AI Key、调用任意 shell 或执行 verify/archive。
- 同名项目、多主机相同路径、路径含空格/中文/符号链接、Windows 和 POSIX 大小写差异均需覆盖。
- 插件升级只获取可信宿主安装包，校验 SHA256；桥接协议不兼容时停止，不修改宿主缓存。

## 分阶段与待决定项

第一阶段：限定一台本机、一台服务器、显式 @ 触发、用户释放后重领，只提供受限桥接与人工回写验证。第二阶段：增加事务转交、断线恢复、多服务器与 MCP 接入。第三阶段才讨论任务通知或聊天调度。

建议先确认：本机是否可持续在线；远端 Codex 的实际运行系统与插件安装方式；是否需要从本机主动派发；断线后的恢复体验；远端报告与安装包如何回传。本轮没有开启监听端口、部署服务、安装远程插件或改变领取协议。
