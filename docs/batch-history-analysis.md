# REQ-047：批次历史的意义与确认记录

## 当前实际作用

批次历史保存每次排期的需求快照、Prompt、hash、引导词版本、提交/取消状态与时间；需求本身持续修改，批次能回答「当时交给 AI 的究竟是什么」。界面点击批次可回到排期视图，已提交批次可取消执行。

批次数据也是当前 Agent 插件安全领取与完成核对的依据：过滤有效 submitted/develop 快照、核对需求/引导词版本、避免过期执行。需求可能累积进入多个批次，取消其中一个不能错误撤回其他批次仍执行的条目。

需求详情的操作历史记录单条需求生命周期，Git Log 记录代码提交；它们不能替代包含多个需求的排期快照。

## Tab 与数据必须区分

可以讨论隐藏/删除独立「批次历史」Tab，但不应因此删除底层批次或 CLI batch list/show。直接删数据会影响版本追溯、取消语义及现有 Pi/Codex/ZCode 插件。

## 初次分析建议（1.4.0）

建议取消独立 Tab 的视觉占位，把「历史排期」作为「排期表」内的次级入口或抽屉；完整保留批次数据、查看 Prompt/hash、状态和必要的取消操作。这降低主导航复杂度，同时保留追溯能力。

本轮未更改或删除该 Tab，等待用户选择：

1. 保留当前独立 Tab（不改）。
2. 推荐：移入排期表的「历史排期」入口，移除独立 Tab，但保留全部数据和 CLI。
3. 仅隐藏独立 Tab，暂不提供新的 UI 入口，仍保留底层数据/CLI（可用性较差，不推荐）。

上述为 1.4.0 时的待确认记录，当时未回写完成，也未自动实施方案 2/3。

## 用户确认与实现（1.5.0）

用户在本轮 REQ-047 明确选择「批次历史移入归档 Tab 的次级入口」，不是移入排期表。

主导航现在只有需求池、排期表、待验证、归档。进入归档默认显示归档需求，通过「批次历史」次级入口查看批次；点击批次仍可回到排期表，既有取消操作保留。批次快照、Prompt/hash、提交/取消状态和 CLI batch list/show 均未删除，也未自动归档数据。
